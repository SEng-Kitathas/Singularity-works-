## Load-bearing code-doctrine extractions

### 1. Truth before theater
- no prestige abstraction
- no beautiful trace addiction without real embodiment
- no elegant story replacing verification

### 2. Typed boundaries over dict spill
- parse early
- type early
- stay typed internally
- serialize late
- dicts are suspect on load-bearing semantic boundaries unless genuinely open-ended

### 3. Anti-pattern to invariant to primitive
For every seam under review ask:
1. What is this step trying to mean?
2. What anti-pattern is the current shape closest to?
3. What invariant should actually govern it?
4. What primitive/boundary/classifier/trace should embody that invariant?
5. What is the most idiomatic low-surprise expression in this runtime/language?
6. What verification anchor proves the new shape is better?
7. What truthful re-architecture is required if the current module shape is itself the anti-pattern?

### 4. Specimen / governance split
Keep executable/trainable bodies separate from governance/sidecar surfaces.
- body/specimen: what executes, trains, reasons, transforms
- governance/sidecar: lineage, adjudication, promotion, contamination, maintenance

### 5. Explicit lifecycle and continuity
- no implied lifecycle hidden only in comments
- no continuity that exists only in operator memory
- state transitions, embodiment, and recovery should be durable and inspectable

### 6. Verification before promotion
No pass is promotable because it sounds principled. Promotion requires the right reality anchors.
Relevant anchors include:
- compile / parse
- verify_build
- self-verification
- public red/green boundary replay
- typed readback / serialization round-trip
- runtime execution

### 7. Re-architecture is allowed when the stronger shape is real
Preserving weak architecture for historical comfort is not doctrine compliance. Re-architecture is justified when it:
- replaces soft convention with explicit invariants
- removes dict/string drift
- collapses duplicated semantics into one primitive substrate
- makes readback harder to fake

### 8. Omega pressure to keep
Use Omega for:
- maximum-attainable quality pressure
- modularity / synergy / elegance / verification / safety / observability / resilience pressure
- holonic declaration pressure: purpose, boundary, interface, invariants, hazards
- parse-don't-validate and proof/verification preference

Do not promote Omega rhetoric blindly into operational truth unless it survives contradiction and embodiment pressure. fileciteturn12file3 fileciteturn12file18
